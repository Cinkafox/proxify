# Proxify — RealIP UDP-прокси для игровых серверов (C#, RawSocket)

Прокси, который передаёт игровой UDP-трафик через туннель и **сохраняет
настоящий IP-адрес клиента** на игровом сервере. Реальный IP подставляется
прокси-клиентом с помощью «сырых» сокетов (`SOCK_RAW` + `IP_HDRINCL`).

Работает на **Windows** и **Linux** (см. раздел «Linux» ниже).

```
                    публичный адрес            подмена настоящего IP
   Клиент игры  ─────►  ПРОКСИ-СЕРВЕР  ─────►  ПРОКСИ-КЛИЕНТ  ─────►  Игровой UDP-сервер
  (игрок, интернет)     (машина A)             (машина B, рядом с сервером)
     ▲                                          │  (RawSocket, source = реальный IP игрока)
     └──────────────────────────────────────────┘
          ответы сервера возвращаются через туннель,
          перехват — сырым сокетом (SIO_RCVALL)
```

Клиент игры видит адрес прокси-сервера, а игровой сервер — настоящие IP
и порты игроков (как если бы они подключались напрямую).

## Состав

| Проект          | Назначение |
|-----------------|------------|
| `Proxy.Server`  | Публичный UDP-порт для клиентов игры + туннель к прокси-клиенту. |
| `Proxy.Client`  | Приём кадров туннеля, впрыск пакетов в локальный игровой сервер с настоящим IP, перехват ответов. |
| `Proxy.Common`  | Общий код: формат кадра, построение/разбор IPv4+UDP пакетов, контрольные суммы, loopback-алиасы. |
| `Proxy.SelfTest`| Самопроверка подмены IP и перехвата ответов (нужны права администратора). |

## Как это работает

1. Игрок отправляет UDP-пакеты на публичный адрес **прокси-сервера** (машина A).
2. Прокси-сервер заворачивает каждый пакет в кадр туннеля вместе с настоящим
   `IP:port` игрока и пересылает **прокси-клиенту** (машина B).
3. Прокси-клиент собирает «сырой» IPv4+UDP пакет:
   - `Source = реальный IP игрока` (подмена),
   - `Destination = 127.0.0.1:<gamePort>` (локальный игровой сервер),
   и отправляет его через RawSocket (`IP_HDRINCL`).
4. Игровой сервер видит пакет, пришедший «от» игрока, и отвечает на этот
   (настоящий) IP:порт.
5. Ответ попадает на loopback-интерфейс машины B, где перехватывается сырым
   сниффером (`SIO_RCVALL`), заворачивается в кадр туннеля и возвращается через
   прокси-сервер игроку. Клиент получает ответ с адреса прокси-сервера — ровно
   туда, куда он отправлял запросы.

### Почему нужны loopback-алиасы

**Windows** (Vista/7/8/10/11) **отбрасывает** «сырые» UDP-пакеты, исходный адрес
которых не назначен ни одному интерфейсу машины. Поэтому настоящий IP игрока
перед отправкой добавляется как `/32`-адрес на loopback-интерфейс (WinAPI
`AddIPAddress`). Это же приводит к тому, что ответы игрового сервера на этот IP
маршрутизируются в loopback, где их и перехватывает сниффер.

**Linux** не требует алиасов для отправки (пакет с чужим source принимается),
но они нужны для возврата ответов сервера: IP игрока добавляется как `/32`-адрес
на `lo` командой `ip addr add <ip>/32 dev lo` (root / CAP_NET_ADMIN), чтобы ответы
сервера уходили в loopback и попадали в сниффер.

## Требования

- Windows + .NET SDK 8 (или новее) для сборки.
- **Права администратора** (Windows) / **root или `CAP_NET_RAW` + `CAP_NET_ADMIN`**
  (Linux) для запуска `Proxy.Client` (RawSocket, перехват ответов, изменение
  loopback-интерфейса). Прокси-сервер прав не требует.
- **Ключ шифрования (`--key`) обязателен** у сервера и прокси-клиента: кадры
  туннеля всегда шифруются AES-256-GCM, сервер без ключа не запускается.
- Linux: нужна утилита `ip` из пакета **iproute2** (есть по умолчанию в
  большинстве дистрибутивов).
- Игровой сервер должен слушать `0.0.0.0:<gamePort>` (или `127.0.0.1:<gamePort>`).
  Если он слушает только внешний IP машины B, укажите этот IP параметром `gameIp`.
- Порт туннеля прокси-клиента (по умолчанию `5600`) должен быть открыт на
  файрволе машины B для приёма кадров от прокси-сервера. UDP-порт игроков
  (по умолчанию `27015`) — открыт на файрволе машины A.

## Сборка

```powershell
dotnet build Proxify.slnx -c Release
```

## Запуск

Аргументы задаются именованными опциями (`--имя значение` или `--имя=значение`,
краткие формы `-p`, `-c` и т.п.). Неизвестные/повторяющиеся опции, неверные
значения и пропущенные обязательные опции приводят к `[ошибка конфигурации] ...`
и выходу с кодом 1. Справка — `--help`.

### Машина A — прокси-сервер

```powershell
# Proxy.Server --port <портИгроков> --key <ключ>
Proxy.Server.exe --port 27015 --key my-secret
```

Обязательные: `--port` (UDP-порт, на который подключаются игроки), `--key`
(общая парольная фраза — **обязательна**, кадры туннеля всегда шифруются).
Адрес прокси-клиента задавать не нужно: сервер определяет его автоматически
по первому кадру туннеля (PING при запуске прокси-клиента) и обновляет при
изменении. Пока связь с прокси-клиентом не установлена, пакеты игроков
отбрасываются с предупреждением в логе.

### Машина B — прокси-клиент (запускать ОТ АДМИНИСТРАТОРА)

```powershell
# Proxy.Client --server <проксиСервер:порт> --tunnel-port <портТуннеля>
#              [--game-ip 127.0.0.1] [--game-port 7777]
#              [--capture true] [--aliases true] --key <ключ>
Proxy.Client.exe --server 1.2.3.4:27015 --tunnel-port 5600 --key my-secret
```

Обязательные: `--server` (адрес прокси-сервера, машина A), `--tunnel-port`
(локальный порт туннеля), `--key` (обязателен, должен совпадать с ключом
сервера). Необязательные (со значениями по умолчанию): `--game-ip` (127.0.0.1),
`--game-port` (7777), `--capture` (true — перехватывать ответы игрового
сервера), `--aliases` (true — добавлять настоящие IP игроков в
loopback-алиасы).

Оба процесса выводят в консоль журнал движения пакетов и завершаются по `Ctrl+C`.
При несовпадении ключей в лог выводится соответствующее предупреждение,
а неразобранные кадры отбрасываются.

### Диагностика при запуске

- **Проверка связи (PING/PONG).** Прокси-клиент при запуске отправляет
  прокси-серверу служебный кадр `PING` с туннельного сокета (3 попытки по 2 с)
  и ждёт `PONG`. Результат печатается как `[диагностика] OK: сервер ... ответил
  на PING за X мс.` Если кадр не разобрался (например, несовпадение ключа),
  сервер пишет `[!] PING ... не разобран (возможно, несовпадение ключа)` — это
  помогает найти проблему ещё до начала трафика.
- **Определение адреса туннеля.** По первому валидному кадру туннеля (PING или
  данные) сервер запоминает адрес прокси-клиента (`[диагностика] Прокси-клиент
  (машина B) определён: ...`). Пока адрес не определён, пакеты игроков
  отбрасываются с предупреждением в логе. Прокси-клиент каждые 10 секунд
  отправляет PING (сердцебиение), поэтому связь восстанавливается сама после
  перезапуска сервера, неудачного стартового PING или смены порта после NAT.
- **Валидация аргументов.** Неверный явно заданный аргумент (порт вне
  `1..65535`, нераспознанный `ip:port`, не-IPv4 `gameIp`, не `true/false` для
  флагов) приводит к сообщению `[ошибка конфигурации] ...` и выходу с кодом 1.
  Отсутствующий или пустой `--key` — тоже ошибка конфигурации.
- **Первый контакт.** Сервер помечает нового игрока и первый кадр от
  прокси-клиента, клиент — первый кадр от сервера (`[диагностика] Получен
  первый кадр туннеля ... — канал работает.`).
- **Статистика.** Раз в минуту (и при остановке клиента) печатается строка
  `[stats]`: `вход` — принятые пакеты/кадры, `отпр` — отправленные кадры,
  `впрыск` — впрыснуто в игру, `перехв` — перехвачено ответов,
  `доставлено` — ответов доставлено игроку, `плохие` — неразобранные кадры.
- Работа происходит по UDP, поэтому даже при неудачном PING клиент продолжает
  работать: связь восстановится, как только появится трафик.

### Linux

Запуск идентичен, но:

```bash
sudo dotnet Proxy.Client.dll --server 1.2.3.4:27015 --tunnel-port 5600 --key my-secret
dotnet Proxy.Server.dll --port 27015 --key my-secret
```

- `Proxy.Client` запускать под `sudo` (нужны `CAP_NET_RAW` для raw-сокета и
  `CAP_NET_ADMIN` для `ip addr add/del`).
- Подмена IP работает без алиасов; алиасы (`ip addr add <ip>/32 dev lo`) добавляются
  автоматически, чтобы ответы сервера возвращались через loopback в сниффер.
- Перехват ответов на Linux выполняется raw IP-сокетом протокола UDP
  (`SOCK_RAW` + `IPPROTO_UDP`) вместо Windows `SIO_RCVALL`.

## Docker (docker-compose)

В репозитории есть готовые примеры для развёртывания в Docker:

| Файл | Сценарий |
|------|----------|
| `docker-compose.local.yml` | Обе машины (A и B) на одной машине — быстрая проверка. |
| `docker-compose.machine-a.yml` | Только прокси-сервер (машина A). |
| `docker-compose.machine-b.yml` | Прокси-клиент + игровой сервер (машина B). |

Образ `client` собирается с игровым UDP-сервером-эхом
(`docker/gamesrv.py`, порт `7777`) — замените его своим сервером, но
запускайте его **в том же контейнере/сетевом пространстве**, что и
`Proxy.Client` (см. `docker/machine-b-entrypoint.sh`), иначе ответы сервера
не попадут в перехватчик на loopback.

Ключ шифрования задаётся переменной окружения `KEY` (или `.env`-файлом):

```powershell
# Локальная проверка всего туннеля:
$env:KEY = "my-secret"
docker compose -f docker-compose.local.yml up -d --build
# с хоста: отправить "HELLO" на 127.0.0.1:27015/udp, в ответ — "HELLO"
docker compose -f docker-compose.local.yml logs -f node-b   # GOT <IP игрока>
docker compose -f docker-compose.local.yml down -v
```

Две машины:

```powershell
# На машине A:
$env:KEY = "my-secret"
docker compose -f docker-compose.machine-a.yml up -d --build

# На машине B (игровой сервер):
$env:MACHINE_A_IP = "1.2.3.4"; $env:KEY = "my-secret"   # тот же ключ!
docker compose -f docker-compose.machine-b.yml up -d --build
```

`proxyclient` (машина B) требует `NET_RAW` и `NET_ADMIN` — они уже указаны в
compose-файлах. Откройте на файрволе: порт игроков `27015/udp` (машина A) и
порт туннеля `5600/udp` (машина B).

## Формат кадра туннеля (big endian)

Внешняя оболочка всех кадров:

```
[2] magic 0xC0DE
[1] тип:
      0x01 — данные без шифрования (далее внутренний кадр данных)
      0x02 — данные с шифрованием    (далее [12]nonce [16]tag [M]ciphertext)
      0x03 — PING  (тело = маркер; шифруется как 0x02)
      0x04 — PONG  (тело = маркер из PING; шифруется)
```

Внутренний кадр данных (расшифрованный текст для типа 0x02):

```
[2] magic 0xC0DE
[1] тип = 0x01 (данные)
[4] IPv4-адрес реального клиента
[2] UDP-порт реального клиента
[2] длина полезной нагрузки
[N] полезная нагрузка (исходная UDP-датаграмма)
```

Зашифрованный кадр (используется всегда — ключ обязателен):

```
[2] magic 0xC0DE
[1] тип = 0x02 (данные, зашифрованы)
[12] nonce
[16] тег аутентификации (GCM)
[M] шифротекст  == расшифровывается во внутренний кадр данных выше
```

Ключ 32 байта получается из парольной фразы через PBKDF2-HMAC-SHA256
(100 000 итераций, salt = первые 16 байт SHA256(фразы)). Шифрование —
AES-256-GCM (встроенный .NET `System.Security.Cryptography.AesGcm`).

Служебные кадры диагностики (тип 0x03/0x04) — тело = маркер PING, шифруется так
же, как данные. PING/PONG не влияют на трафик игроков: прокси-клиент использует
их для стартовой проверки связи и сердцебиения, а сервер — для определения
адреса туннеля.

## Ограничения и примечания

- Только IPv4.
- Сервер принимает все кадры на порту игроков и отличает их от пакетов игры по
  магику `0xC0DE` и типу кадра, а адрес прокси-клиента определяет по первому
  валидному кадру (PING/данные). Игровой пакет, начинающийся с байтов `0xC0 DE`,
  может быть ошибочно принят за кадр туннеля — при несовпадении ключа он будет
  отброшен как неразобранный. Если игровой протокол использует такой заголовок,
  выносите туннель на отдельный UDP-порт.
- Подмена IP — фича, которую Windows ограничивает; работоспособность зависит
  от сборки ОС. На десктопных Windows пакет с чужим Source принимается только
  если адрес назначен локальному интерфейсу — поэтому используются алиасы.
- Если перехват ответов включён, ответ игрового сервера уходит в loopback и
  больше **не покидает** машину B напрямую — клиент получает его только через
  туннель. Это устраняет дубликаты для «соединённых» UDP-сокетов клиентов.
- Перехват ответов работает через raw-сокет (`SIO_RCVALL` на Windows, raw
  `IPPROTO_UDP` на Linux). Если на вашей сборке перехват не работает, попробуйте
  `captureReplies=false` — тогда ответы будут уходить игроку напрямую (подходит,
  если клиент принимает UDP-ответы от любого источника).
- Программа использует только встроенные средства Windows (WinAPI `iphlpapi`,
  Winsock RawSocket) и не требует сторонних драйверов вроде WinPcap/WinDivert.

## Структура проекта

```
Proxy.Common/
  Frame.cs              кодирование/декодирование кадров туннеля
  TunnelCipher.cs       AES-256-GCM + PBKDF2 для шифрования кадров
  Packets.cs            сборка и разбор IPv4+UDP пакетов
  Checksum.cs           контрольные суммы IPv4/UDP
  PlatformSockets.cs    «сырые» сокеты для Windows (SIO_RCVALL) и Linux (raw IPPROTO_UDP)
  LoopbackAliasManager.cs  добавление/удаление IP игроков на loopback (WinAPI / ip)
  NetUtils.cs              вспомогательные утилиты (разбор ip:port, портов, флагов)
  ArgParser.cs             разбор аргументов --имя значение (обязательные/дефолты/--help)
  TunnelStats.cs           счётчики трафика и строка [stats]
Proxy.Server/Program.cs     прокси-сервер (реле игроков и туннеля)
Proxy.Client/Program.cs     конфигурация и запуск прокси-клиента
Proxy.Client/RawInjector.cs  RawSocket-впрыск с настоящим IP (IP_HDRINCL)
Proxy.Client/ReplySniffer.cs перехват ответов и возврат в туннель
Proxy.SelfTest/Program.cs    самопроверка
scripts/test-tunnel.ps1      интеграционный тест туннеля
Dockerfile                   трёхстадийная сборка образов server/client
docker/gamesrv.py            игровой UDP-сервер-эхо для примера (порт 7777)
docker/machine-b-entrypoint.sh  старт игрового сервера и прокси-клиента в контейнере
docker-compose.*.yml         примеры развёртывания (см. раздел «Docker»)
```
