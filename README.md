# Proxify — RealIP UDP-прокси для игровых серверов (C#, RawSocket)

Прокси, который передаёт игровой UDP-трафик через туннель и **сохраняет
настоящий IP-адрес клиента** на игровом сервере. Реальный IP подставляется
прокси-клиентом с помощью «сырых» сокетов (`SOCK_RAW` + `IP_HDRINCL`).

Один публичный сервер (машина A) обслуживает **несколько** прокси-клиентов
(машины B). Каждый клиент аутентифицируется асимметрично (ECDSA P-256),
а кадры шифруются отдельным сессионным ключом (ECDH P-256 + HKDF + AES-256-GCM).

Работает на **Windows** и **Linux** (см. раздел «Linux» ниже).

```
                    публичный адрес            подмена настоящего IP
   Клиент игры  ─────►  ПРОКСИ-СЕРВЕР  ─────►  ПРОКСИ-КЛИЕНТ  ─────►  Игровой UDP-сервер
  (игрок, интернет)     (машина A)             (машина B, рядом с сервером)
     ▲                                          │  (RawSocket, source = реальный IP игрока)
     └──────────────────────────────────────────┘
          ответы сервера возвращаются через туннель,
          перехват — сырым сокетом (SIO_RCVALL)
```

Клиент игры видит адрес прокси-сервера, а игровой сервер — настоящие IP
и порты игроков (как если бы они подключались напрямую).

## Состав

| Проект          | Назначение |
|-----------------|------------|
| `Proxify.Server`  | Публичные UDP-порты игроков (по одному на каждого клиента из конфига) + туннель к прокси-клиентам. |
| `Proxify.Client`  | Приём кадров туннеля, впрыск пакетов в локальный игровой сервер с настоящим IP, перехват ответов. |
| `Proxify.Common`  | Общий код: криптография P-256 (ключи, подпись, ECDH+HKDF), конфиг сервера, формат кадра, raw-пакеты, loopback-алиасы. |
| `Proxify.SelfTest`| Самопроверка подмены IP и перехвата ответов (нужны права администратора). |

## Аутентификация и сессионный ключ

У каждого прокси-клиента есть пара ключей **P-256**:

- **закрытый ключ** (PKCS#8 PEM) хранится на машине B — подписывает кадр Auth,
  доказывая личность клиента;
- **открытый ключ** (SPKI PEM) регистрируется в **конфиге сервера** (машина A).

Рукопожатие (кадры Auth/AuthAck идут без шифрования оболочки):

1. Клиент генерирует эфемерный ключ ECDH и подписывает своим закрытым ключом
   `"proxify-auth-v1"||X||Y||nonce` (ECDSA P-256, IEEE P1363).
2. Сервер проверяет подпись по всем зарегистрированным публичным ключам,
   опознаёт клиента и отвечает AuthAck: свой эфемерный ключ ECDH +
   «доказательство» (echo nonce + игровые параметры), зашифрованное
   сессионным ключом.
3. Обе стороны вычисляют один и тот же **сессионный ключ**:
   `HKDF-SHA256(ECDH(свой приватный, чужой публичный), salt = пустой,
   info = "proxify-session-v1", 32 байта)` — им шифруются все кадры данных.

Сервер принимает только клиентов, чей публичный ключ есть в конфиге; чужой ключ
отвергается (см. `scripts/test-tunnel.ps1`, негативный тест).

## Как это работает

1. Игрок отправляет UDP-пакеты на публичный UDP-порт своего клиента на
   **прокси-сервере** (машина A).
2. Прокси-сервер заворачивает каждый пакет в кадр туннеля вместе с настоящим
   `IP:port` игрока и пересылает **прокси-клиенту** (машина B).
3. Прокси-клиент собирает «сырой» IPv4+UDP пакет:
   - `Source = реальный IP игрока` (подмена),
   - `Destination = 127.0.0.1:<gamePort>` (локальный игровой сервер),
   и отправляет его через RawSocket (`IP_HDRINCL`).
4. Игровой сервер видит пакет, пришедший «от» игрока, и отвечает на этот
   (настоящий) IP:порт.
5. Ответ попадает на loopback-интерфейс машины B, где перехватывается сырым
   сниффером (`SIO_RCVALL`), заворачивается в кадр туннеля и возвращается через
   прокси-сервер игроку. Клиент получает ответ с адреса прокси-сервера — ровно
   туда, куда он отправлял запросы.

Обработка пакетов многопоточная: циклы приёма (UDP-игроки, туннель, TCP-клиенты)
только получают данные и ставят их в ограниченные очереди, а обработкой и
отправкой занимается пул воркеров (2–8 потоков в зависимости от числа ядер).
Это разгружает приём (медленная отправка не стопорит приём новых пакетов) и
позволяет обрабатывать пакеты разных игроков/соединений параллельно. Записи в
одно TCP-соединение сериализуются, чтобы не перемешивать байты потока.

### TCP-проксирование (поле конфига клиента `tcp: true`)

Кроме UDP, через тот же туннель можно проксировать и **TCP-трафик** игровых
клиентов. Включается **в конфиге сервера** для конкретного клиента
(`tcp: true`, `tcpPort`). Клиент узнаёт о включённом TCP автоматически:
из конфига в AuthAck и из флага в каждом PONG.

1. Игрок подключается по TCP к TCP-порту своего клиента **прокси-сервера**
   (машина A) — по умолчанию тот же номер, что и UDP-порт игроков (`tcpPort`).
2. Сервер присваивает соединению `connId` и уведомляет прокси-клиента кадром
   `TcpOpen` (вместе с IP:порт игрока).
3. Прокси-клиент сам устанавливает TCP-соединение с игровым сервером
   (`gameIp:gamePort`) и передаёт данные кадрами `TcpData` в обе стороны.
4. Закрытие соединения (любой стороной) передаётся кадром `TcpClose`.

Ограничение: в отличие от UDP, TCP **не позволяет подменить исходный IP**, поэтому
игровой сервер видит соединения с адреса машины B, а не игрока. Трафик между
машинами A и B, как и для UDP, идёт по зашифрованному UDP-туннелю.

#### Оптимизация TCP под HTTP (в т.ч. chunked)

При чтении из TCP-сокета данные не пересылаются «как есть», а проходят через
`TcpFrameBatcher` (обе стороны туннеля). Политика отправки оптимизирована под
HTTP и потоковые протоколы, оставаясь прозрачной для любых других TCP-приложений:

- **граница HTTP-заголовков** (`CRLF CRLF`) — накопленное отправляется немедленно:
  запрос/ответ доходит без задержки (в т.ч. для keep-alive, где каждый следующий
  обмен снова начинается с заголовков);
- **поток после заголовков** — если буфер заканчивается на `CRLF` (граница чанка
  chunked-кодирования или строка SSE), данные уходят сразу, поэтому браузер
  видит прогресс потокового ответа;
- **Nagle-подобное объединение** — во всех остальных случаях мелкие сегменты TCP
  удерживаются ~5 мс и отправляются одним кадром (меньше UDP-датаграмм и
  накладных расходов);
- **размер кадра ≤ 1400 байт** — UDP-датаграмма не фрагментируется на уровне IP
  (MTU 1500), что повышает надёжность доставки; большие потоки делятся на
  несколько кадров и склеиваются на приёмной стороне в исходный порядок;
- `TCP_NODELAY` включён на TCP-сокетах обеих сторон, чтобы не срабатывал
  локальный алгоритм Нейгла поверх уже объединённых кадров.


### Почему нужны loopback-алиасы

**Windows** (Vista/7/8/10/11) **отбрасывает** «сырые» UDP-пакеты, исходный адрес
которых не назначен ни одному интерфейсу машины. Поэтому настоящий IP игрока
перед отправкой добавляется как `/32`-адрес на loopback-интерфейс (WinAPI
`AddIPAddress`). Это же приводит к тому, что ответы игрового сервера на этот IP
маршрутизируются в loopback, где их и перехватывает сниффер.

**Linux** не требует алиасов для отправки (пакет с чужим source принимается),
но они нужны для возврата ответов сервера: IP игрока добавляется как `/32`-адрес
на `lo` командой `ip addr add <ip>/32 dev lo` (root / CAP_NET_ADMIN), чтобы ответы
сервера уходили в loopback и попадали в сниффер.

## Требования

- Windows + .NET SDK 8 (или новее) для сборки.
- **Права администратора** (Windows) / **root или `CAP_NET_RAW` + `CAP_NET_ADMIN`**
  (Linux) для запуска `Proxify.Client` (RawSocket, перехват ответов, изменение
  loopback-интерфейса). Прокси-сервер прав не требует.
- Пара ключей P-256 у каждого прокси-клиента и регистрация его публичного ключа
  в конфиге сервера (см. «Подготовка ключей» ниже). Без ключа сервер не запускается.
- Linux: нужна утилита `ip` из пакета **iproute2** (есть по умолчанию в
  большинстве дистрибутивов).
- Игровой сервер должен слушать `0.0.0.0:<gamePort>` (или `127.0.0.1:<gamePort>`).
  Если он слушает только внешний IP машины B, укажите этот IP полем `gameIp`
  в конфиге сервера.
- Открытые порты нужны **только на машине A**: UDP-порт игроков каждого клиента
  (по умолчанию `27015`) и порт туннеля (по умолчанию `5600`). Машина B портов
  наружу не открывает — прокси-клиент сам устанавливает исходящее UDP-соединение
  на порт туннеля машины A.

## Сборка

```powershell
dotnet build Proxify.slnx -c Release
```

## Подготовка ключей и конфига

**Машина B** (один раз на каждого клиента):

```powershell
Proxify.Client --keygen C:\keys\client1
# создаёт C:\keys\client1\client-private.pem  (остаётся на B)
#          C:\keys\client1\client-public.pem  (передать на машину A)
```

**Машина A**: положите `client-public.pem` в отдельный каталог и сгенерируйте
конфиг-шаблон:

```powershell
Proxify.Server --configgen C:\proxify\config
# создаёт C:\proxify\config\server.json, ссылающийся на client-public.pem
```

При необходимости отредактируйте `server.json` (добавьте клиентов, смените порты).

## Конфиг сервера (`server.json`)

```json
{
  "clients": [
    {
      "name": "client1",
      "publicKey": "client-public.pem",
      "port": 27015,
      "gameIp": "127.0.0.1",
      "gamePort": 7777,
      "capture": true,
      "aliases": true,
      "tcp": false,
      "tcpPort": 27015
    }
  ]
}
```

| Поле | Обязательное | Описание |
|------|--------------|----------|
| `name` | нет | Отображаемое имя клиента (для логов). |
| `publicKey` | да | Открытый ключ клиента: путь к PEM-файлу (относительно каталога конфига) или сам PEM-текст. |
| `port` | да | UDP-порт игроков на машине A (не должен совпадать с портом другого клиента и с `--tunnel-port`). |
| `gameIp` | да | IPv4-адрес игрового сервера (на машине B), куда впрыскиваются пакеты. |
| `gamePort` | да | UDP-порт игрового сервера. |
| `capture` | нет | `true` — перехватывать ответы игрового сервера и возвращать их через туннель (по умолчанию `true`). |
| `aliases` | нет | `true` — добавлять настоящие IP игроков в loopback-алиасы (по умолчанию `true`). |
| `tcp` | нет | `true` — включить TCP-проксирование для этого клиента (по умолчанию `false`). |
| `tcpPort` | нет | TCP-порт игроков на машине A (по умолчанию равен `port`). |

Один сервер обслуживает нескольких клиентов — добавьте несколько элементов
в `clients` (у каждого свой `port` и свой публичный ключ).

## Запуск

Аргументы задаются именованными опциями (`--имя значение` или `--имя=значение`).
Неизвестные/повторяющиеся опции и неверные значения приводят к
`[ошибка конфигурации] ...` и выходу с кодом 1. Справка — `--help`.

### Машина A — прокси-сервер

```powershell
Proxify.Server.exe --config C:\proxify\config\server.json --tunnel-port 5600
```

Обязательные: `--config` (путь к `server.json`) и `--tunnel-port` (отдельный
UDP-порт туннеля — на него прокси-клиенты шлют кадры; не должен совпадать
с портами игроков из конфига).

Вспомогательный режим: `Proxify.Server --configgen <каталог>` генерирует
шаблон `server.json` из `client-public.pem` в этом каталоге.

### Машина B — прокси-клиент (запускать ОТ АДМИНИСТРАТОРА)

```powershell
Proxify.Client.exe --server 1.2.3.4:5600 --key C:\keys\client1\client-private.pem
```

Обязательные: `--server` (адрес машины A; `host` или `host:порт туннеля`) и
`--key` (закрытый ключ этого клиента). Если порт туннеля не указан в `--server`,
задайте его отдельно `--tunnel-port`.

Все игровые параметры (gameIp, gamePort, capture, aliases, tcp) клиент получает
**от сервера** в AuthAck — своих флагов у него больше нет.

Вспомогательный режим: `Proxify.Client --keygen <каталог>` генерирует пару ключей.

Локальный порт туннеля клиент выбирает автоматически (эфемерный) — портов
наружу на машине B открывать не нужно.

Оба процесса выводят в консоль журнал движения пакетов и завершаются по `Ctrl+C`.

### Диагностика при запуске

- **Рукопожатие.** Клиент при старте выполняет Auth (3 попытки по 3 с) и ждёт
  AuthAck. Результат печатается как `[auth] OK: авторизация за X мс.` и
  `[auth] Получена конфигурация от сервера: игра ...`. Если сервер не ответил,
  клиент выводит подсказки (сервер запущен? публичный ключ зарегистрирован?
  файрвол машины A пропускает UDP на порт туннеля?).
- **Сердцебиение и повторная авторизация.** Клиент каждые 10 секунд шлёт
  зашифрованный PING. Если PONG давно не было (30 с), сессия считается протухшей
  и клиент выполняет повторный Auth — связь восстанавливается сама после
  перезапуска сервера или смены порта после NAT.
- **Защита от чужого клиента.** Сервер принимает кадры туннеля только после
  успешного Auth: подпись Auth проверяется по всем зарегистрированным ключам,
  чужой клиент отвергается (`[!] Auth ... подпись не соответствует ни одному
  зарегистрированному ключу`).
- **Статистика.** Раз в минуту (и при остановке клиента) печатается строка
  `[stats]`: `вход` — принятые пакеты/кадры, `отпр` — отправленные кадры,
  `впрыск` — впрыснуто в игру, `перехв` — перехвачено ответов,
  `доставлено` — ответов доставлено игроку, `плохие` — неразобранные кадры.

### Linux

Запуск идентичен, но:

```bash
sudo dotnet Proxify.Client.dll --server 1.2.3.4:5600 --key /etc/proxify/client-private.pem
dotnet Proxify.Server.dll --config /etc/proxify/server.json --tunnel-port 5600
```

- `Proxify.Client` запускать под `sudo` (нужны `CAP_NET_RAW` для raw-сокета и
  `CAP_NET_ADMIN` для `ip addr add/del`).
- Подмена IP работает без алиасов; алиасы (`ip addr add <ip>/32 dev lo`) добавляются
  автоматически, чтобы ответы сервера возвращались через loopback в сниффер.
- Перехват ответов на Linux выполняется raw IP-сокетом протокола UDP
  (`SOCK_RAW` + `IPPROTO_UDP`) вместо Windows `SIO_RCVALL`.

## Docker (docker-compose)

В репозитории есть готовые примеры для развёртывания в Docker:

| Файл | Сценарий |
|------|----------|
| `docker-compose.local.yml` | Обе машины (A и B) на одной машине — быстрая проверка. |
| `docker-compose.machine-a.yml` | Только прокси-сервер (машина A). |
| `docker-compose.machine-b.yml` | Прокси-клиент + игровой сервер (машина B). |
| `docker-compose.machine-b.host.yml` | Прокси-клиент в host-режиме, игровой сервер на хосте машины B. |

Перед запуском подготовьте `deploy/` в корне репозитория:

```powershell
# На машине B (или локально для local.yml) — пара ключей:
Proxify.Client --keygen .\deploy
# На машине A — конфиг (publicKey ссылается на client-public.pem):
Proxify.Server --configgen .\deploy
```

В `server.json` при необходимости добавьте клиентов/поменяйте порты. Файлы
монтируются в контейнеры: `server.json` и `client-public.pem` — в образ сервера,
`client-private.pem` — в образ клиента. Пути по умолчанию переопределяются
переменными окружения `SERVER_CONFIG`, `CLIENT_PUBLIC_KEY`, `CLIENT_KEY`.

Если игровой сервер запущен на хосте машины B (а не в контейнере), прокси-клиент
должен работать в host-режиме (`network_mode: host`), иначе Docker NAT перепишет
подменённый IP игрока (сервер увидит шлюз docker-сети вместо настоящего IP), а
ответы игры не попадут в сниффер. См. `docker-compose.machine-b.host.yml`.

Образ `client` собирается с игровым UDP-сервером-эхом
(`docker/gamesrv.py`, порт `7777`) — замените его своим сервером, но
запускайте его **в том же контейнере/сетевом пространстве**, что и
`Proxify.Client` (см. `docker/machine-b-entrypoint.sh`), иначе ответы сервера
не попадут в перехватчик на loopback.

```powershell
# Локальная проверка всего туннеля (после подготовки ./deploy):
docker compose -f docker-compose.local.yml up -d --build
# с хоста: отправить "HELLO" на 127.0.0.1:27015/udp, в ответ — "HELLO"
docker compose -f docker-compose.local.yml logs -f node-b   # GOT <IP игрока>
docker compose -f docker-compose.local.yml down -v

# Две машины — на машине A:
docker compose -f docker-compose.machine-a.yml up -d --build
# На машине B (игровой сервер):
$env:MACHINE_A_IP = "1.2.3.4"
docker compose -f docker-compose.machine-b.yml up -d --build
```

`proxyclient` (машина B) требует `NET_RAW` и `NET_ADMIN` — они уже указаны в
compose-файлах. Откройте на файрволе **машины A** порты: игроков `27015/udp`
и туннеля `5600/udp`. На машине B портов открывать не нужно.

## Формат кадра туннеля (big endian)

Внешняя оболочка всех кадров:

```
[2] magic 0xC0DE
[1] тип:
      0x01 — данные без шифрования (далее внутренний кадр данных)
      0x02 — данные с шифрованием    (далее [12]nonce [16]tag [M]ciphertext)
      0x03 — PING  (тело = маркер; шифруется как 0x02)
      0x04 — PONG  (тело = маркер из PING + [1] флаг TCP; шифруется)
      0x05 — TCP: открытие соединения (сервер -> клиент; тело = [4]ip [2]порт [4]connId)
      0x06 — TCP: данные (обе стороны; тело = [4]connId [N]данные)
      0x07 — TCP: закрытие (обе стороны; тело = [4]connId)
      0x08 — AUTH  (рукопожатие, БЕЗ шифрования)
      0x09 — AUTH_ACK (рукопожатие, БЕЗ шифрования оболочки)
```

Внутренний кадр данных (расшифрованный текст для типа 0x02):

```
[2] magic 0xC0DE
[1] тип = 0x01 (данные)
[4] IPv4-адрес реального клиента
[2] UDP-порт реального клиента
[2] длина полезной нагрузки
[N] полезная нагрузка (исходная UDP-датаграмма)
```

Кадр AUTH (0x08, plaintext):

```
[1]  версия = 1
[32] X эфемерного ключа ECDH клиента
[32] Y эфемерного ключа ECDH клиента
[16] nonce
[64] подпись ECDSA P-256 (IEEE P1363) по "proxify-auth-v1"||X||Y||nonce
```

Кадр AUTH_ACK (0x09, plaintext):

```
[32] X эфемерного ключа ECDH сервера
[32] Y эфемерного ключа ECDH сервера
[N]  «доказательство», зашифрованное сессионным ключом:
     plaintext = [16] echo nonce [1] флаги [4] gameIp [2] gamePort
     флаги: бит 0 = capture, бит 1 = aliases, бит 2 = tcp
```

Зашифрованный кадр данных (тип 0x02):

```
[2] magic 0xC0DE
[1] тип = 0x02 (данные, зашифрованы)
[12] nonce
[16] тег аутентификации (GCM)
[M] шифротекст  == расшифровывается во внутренний кадр данных выше
```

**Ключи.** Сессионный ключ (32 байта) выводится из ECDH при рукопожатии:
`HKDF-SHA256(ECDH-секрет, salt = пустой, info = "proxify-session-v1")`.
Шифрование — AES-256-GCM (встроенный .NET `System.Security.Cryptography.AesGcm`).
Формат зашифрованного блока — `[nonce][tag][ciphertext]`.

PING/PONG не влияют на трафик игроков: прокси-клиент использует их для
сердцебиения (каждые 10 с), а сервер — для определения адреса туннеля.
Дополнительно сервер добавляет в PONG байт признака TCP-проксирования,
поэтому клиент знает о включённом `tcp` ещё до первого TCP-соединения.

## Ограничения и примечания

- Только IPv4.
- Туннель живёт на отдельном UDP-порту (`--tunnel-port`), отдельном от портов
  игроков (из конфига). Кадры туннеля не пересекаются с пакетами игры.
- Подмена IP — фича, которую Windows ограничивает; работоспособность зависит
  от сборки ОС. На десктопных Windows пакет с чужим Source принимается только
  если адрес назначен локальному интерфейсу — поэтому используются алиасы.
- Если перехват ответов включён, ответ игрового сервера уходит в loopback и
  больше **не покидает** машину B напрямую — клиент получает его только через
  туннель. Это устраняет дубликаты для «соединённых» UDP-сокетов клиентов.
- Перехват ответов работает через raw-сокет (`SIO_RCVALL` на Windows, raw
  `IPPROTO_UDP` на Linux). Если на вашей сборке перехват не работает, поставьте
  `"capture": false` в конфиге — тогда ответы будут уходить игроку напрямую
  (подходит, если клиент принимает UDP-ответы от любого источника).
- Программа использует только встроенные средства Windows (WinAPI `iphlpapi`,
  Winsock RawSocket) и не требует сторонних драйверов вроде WinPcap/WinDivert.
